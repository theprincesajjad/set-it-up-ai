# Security review: public endpoints added this month

Reviewed 2026-10-25 against `apps/api` at the head of `main` plus the fixes listed below. Scope: every endpoint that
can be reached without a Local Loyalty sign-in, or by a secret link, that shipped in October (restaurant pack, service
desk, BIA campaigns, onboarding reminders, phone and WhatsApp channels). Tests are in
`apps/api/test/public-security.test.ts` unless another file is named.

Follow-up the same day (`perf` pass): the three leftovers below are closed. Ticket status links now expire, unsubscribe links no longer
change anything on GET, and the rate-limit counters are documented as per process with an optional shared (Postgres) store.
Tests are in `apps/api/test/service-ops.test.ts` (ticket expiry), `messaging.test.ts` and `opt-out.test.ts` (unsubscribe),
`rate-limit-store.test.ts` (counters).

Result key: **pass** (no change needed), **fixed** (finding fixed in this review, test added), **accepted** (a known
trade-off, reason given), **open** (needs a decision outside the code).

## Controls that apply to all of them

| Check | How it works | Result |
| --- | --- | --- |
| Token entropy | Every link token comes from `randomToken(n)` (`node:crypto` `randomBytes`, base64url): driver 24 bytes (192 bits), catering approval 24, split pay 18 (144), ticket status 18 (144), review 16 (128). Unsubscribe tokens are a 128-bit HMAC-SHA256 prefix. Nothing uses `Math.random`. Short tokens (< 16 characters) are refused before the database is touched. | pass |
| Enumeration guard | New: a per-address counter of links that did not exist (404, 410, and 400/403 where the credential is in the query string) on the secret-link pages. 40 misses in 10 minutes from one address gets 429 on those pages for the rest of the window; ordinary public pages, other addresses and form typos are unaffected. The tokens are unguessable, so this is defence in depth and an early sign of a scanner. `lib/rate-limit.ts` sweeps stale keys so the counters cannot grow without bound. The counters are per API process unless `RATE_LIMIT_STORE=postgres` (next row). | fixed |
| Client address behind a proxy | `trustProxy: true` trusted every `X-Forwarded-For` hop, so a caller could pick its own address and walk around every per-address limit. Now `TRUST_PROXY_HOPS` (production default 1, the load balancer; development and test trust the header). Set it to the real number of hops in the hosting config. | fixed |
| Blanket rate limit | `@fastify/rate-limit`, 300 requests a minute per user or address, on everywhere except `NODE_ENV=test`. | pass |
| Rate-limit counters across instances | Every per-key counter (the enumeration guard, driver links, split pay, catering and public-lead inquiries) and the blanket cap above lived in the memory of one API process, so behind a load balancer with N instances each limit was really up to N times higher. Documented in `lib/rate-limit.ts`, `.env.example` and `api/public.md`. New: `RATE_LIMIT_STORE=postgres` keeps them in the `rate_limit_counters` table (migration `0020_perf`): one fixed window per key started by its first hit, one atomic upsert per check, expired rows removed by the `ratelimit.sweep` job, the blanket cap through a `@fastify/rate-limit` store on the same table. Default stays `memory`: the shared store costs an extra write on every request, so it is for deployments that run more than one instance. The two inquiry limiters that kept their own private maps (`services/catering.ts`, `services/public-leads.ts`) now use the same module. No Redis store is built in; `@fastify/rate-limit` also accepts an `ioredis` client if an instance fleet outgrows the table. | fixed (default per process, documented; shared store optional) |
| Error leakage | The error handler already returned `{ code, message }` only for unexpected errors (500 "Something went wrong"). Several services attached the provider's error text to a 502 as `details.cause` (split pay, tiffin payment, order payment, deposit refunds), and the Stripe webhook echoed the verifier's `reason`. The handler now logs those and never sends `cause` (or the signature `reason`) to the caller. | fixed |
| CSV injection | `toCsv` is the only CSV writer (the customer exports and the BIA board report). It prefixes `=`, `+`, `-`, `@`, tab and carriage return with `'`, quotes commas, quotes and newlines, and leaves numbers alone. | pass (tests added) |

## Endpoint by endpoint

| Endpoint | Auth and token | Expiry | Rate limit | IDOR | Error leakage | Result |
| --- | --- | --- | --- | --- | --- | --- |
| Driver links, `GET/POST /v1/public/tiffin/driver/:token[...]` (page `/d/<token>`) | 192-bit token, one per route and day, created by staff. | 23:59 Toronto on the run date, then 410 `link_expired`. | 120 requests a minute per token (limiter now swept; it grew without bound), plus the address guard. "Running late" once every 15 minutes. | A stop is only updated if it belongs to the link's merchant, date and route (`driverStop`); another route's delivery id is a 404 (`tiffin-driver.test.ts`). The page shows customer name, phone and address for that route only; the driver needs them. | Unknown, short and other-day tokens are the same 404 / 410 bodies. | fixed |
| Ticket status, `GET /v1/public/tickets/:token` (`/t/<token>`) | 144-bit token on the ticket, created at check-in. | New: an open ticket's link always works; a closed one (`picked_up`, `cancelled`) works for 30 days after its last closing event, then `410 link_expired` (the body carries only the shop's name and phone) and the web page shows a friendly "this status link has expired, contact {shop}" page with a call button, in four languages. The constant is `TICKET_LINK_DAYS_AFTER_CLOSE` in `packages/shared/src/service-rules.ts`. Before this the page stayed readable forever. It is read-only and shows only customer-visible events, the item, the shop's phone and address; no customer name, phone or email. | Address guard (an expired link counts as a miss). | Token to one ticket; no ids in the response that other endpoints accept. | Uniform 404; the 410 names only the shop. | fixed |
| Pay intent, `GET /v1/public/payments/:paymentIntentId?cs=` (`/pay/intent/...`) | The PaymentIntent client secret in `cs` is the credential; it is compared in constant time with the provider's value. | Follows the Stripe intent (a cancelled intent shows `canceled`). | Address guard; an unknown intent never reaches Stripe. | The intent id is resolved through our own tables (tiffin charge, hall deposit, catering deposit, order), so only intents we created are visible; a wrong or missing secret looks exactly like an unknown id. | 404 only. | pass |
| Pay setup, `GET /v1/public/payments/setup/:setupIntentId?cs=` | Same rule with the SetupIntent client secret. | Follows the Stripe setup intent. | Address guard. | Resolved through `tiffin_subscriptions.setup_intent_id`. | 404 only. | pass |
| Split pay, `GET/POST /v1/public/splits/:token[/pay]` | 144-bit token per guest share; feature gate `restaurant.split_bills`. | Share is dead once the bill is closed or the share is paid (409). | New: each pay attempt with a different tip creates a Stripe PaymentIntent, so a leaked link could spam them. Now 20 attempts an hour per link (429), plus the address guard. Tip capped at $1,000. | Token resolves to one share; the pay amount comes from the share, never the request. | The 502 no longer carries Stripe's error text. | fixed |
| Public reviews, `GET/POST /v1/public/reviews/:token[/google-opened]` | 128-bit token per request, sent by SMS, email or WhatsApp. | New: new answers stop 90 days after the request (410 `link_expired`); before this a link in an old message worked forever. | Address guard. One answer per request (atomic claim), so repeats cannot change the rating. Feedback limited to 2,000 characters and stored and emailed as plain text. | Token to one request. The page shows the shop name, the Google link and the guest's own rating. | Uniform 404. | fixed |
| Catering approval, `GET/POST /v1/public/catering/:token[/approve]` (`/e/<token>`) | 192-bit token, only valid after the quote is sent. Signature name, IP and user agent are stored. | New: a quote cannot be signed after the event date (410 `quote_expired`). Re-approving an approved quote is idempotent. | Address guard. Public inquiries (`POST /public/shops/:slug/catering/inquiries`): 10 an hour per address, feature gated. | Token to one event; the inquiry reply returns a reference and never the approval token. Staff-only fields (signature IP) are not in the public view. | Uniform 404. | fixed |
| Live campaigns, `GET /v1/public/live-campaigns`, `GET /v1/public/campaigns/:id` | None, by design (the shopper page). | Only campaigns that are live now; by id only `scheduled`, `live` and `ended` (never drafts). | Blanket limit. | Campaign fields are marketing copy, dates, goal and the participating shop names; no customer data. | n/a | pass |
| Founding spots, `GET /v1/public/restaurants/founding` | None, by design (marketing site). | n/a | Blanket limit; `Cache-Control: public, max-age=300`. | Per-area counts only (taken of 20), no shop names. | n/a | pass |
| Neighbourhood report, `GET /v1/neighbourhoods/:id/report` (JSON or CSV) | Signed in, and `requireNeighbourhoodManager` (manager of that street, or admin). Not public. | n/a | Blanket limit. | A manager of street A gets 403 for street B. | Aggregates only; CSV filename is a slug of the street name. CSV cells go through `toCsv` (campaign, shop and street names such as `=cmd...` are prefixed). | pass (test added) |
| Onboarding and marketing unsubscribe, `GET/POST /v1/public/onboarding/unsubscribe?m=&t=` and `GET/POST /v1/public/messaging/unsubscribe` | `t` is the first 128 bits of an HMAC-SHA256 of the shop (nudges) or member id; compared in constant time. A wrong token is 400 and counts toward the address guard. | None, on purpose: CASL requires an unsubscribe link to keep working. | Address guard. | The token is bound to the shop or member id in `m`; it cannot be reused for another. | Pages escape the shop name (`& < > " '`) and are served `no-store`, `noindex`, `Referrer-Policy: no-referrer` with a CSP that lets the form post only to our own origin. | fixed: **a GET changes nothing.** The link opens a confirm page (in the reader's language, four of them) whose button POSTs the same token back. A mail scanner, link preview or prefetcher can no longer unsubscribe anyone. The POST is the only call that acts; it answers a page to a browser form post and JSON to everything else, which keeps **RFC 8058 one-click** working: campaign and reminder emails carry `List-Unsubscribe: <url>` and `List-Unsubscribe-Post: List-Unsubscribe=One-Click`, and a mail app POSTs `List-Unsubscribe=One-Click` to that URL |
| Phone webhook, `POST /v1/webhooks/phone/:merchantId` | Twilio signature (`X-Twilio-Signature`) over the full public URL and the form fields, constant-time compare. With no auth token configured, unsigned calls are accepted only outside production. | n/a | Blanket limit. | The shop comes from the path; a call is stored once per `CallSid` (a replay does not create a second order). | 403 `invalid_signature`, no detail. | pass (production-mode test for every webhook) |
| WhatsApp webhook, `GET/POST /v1/webhooks/whatsapp` | POST: `X-Hub-Signature-256` HMAC of the raw body with the app secret, constant time; GET handshake needs the configured verify token (none configured means no handshake). Unsigned POSTs are accepted only outside production. | n/a | Blanket limit. | Messages are matched to a shop by Meta phone number id; processed once per message id. | 403 `invalid_signature`, no detail. | pass |
| Other inbound webhooks, `POST /v1/webhooks/stripe`, `twilio/sms`, `square`, `clover`, `shopify`, `lightspeed`, `toast` | Provider signatures; Stripe through the SDK verifier; Twilio SMS refuses everything when no token is set, in every environment. | Stripe events are processed once per event id. | Blanket limit. | n/a | The Stripe 400 no longer echoes the verifier's reason. `POST /v1/payments/fake/simulate` is a 404 in production. | fixed |

## Support access (same review)

Admin and rep writes inside a shop now need an active support session with a reason (`403 support_session_required`);
reads stay open. See `apps/api/test/support-sessions.test.ts`.

## Open items

1. Set `TRUST_PROXY_HOPS` in the production environment to the real number of proxies (default 1).
2. Set `RATE_LIMIT_STORE=postgres` as soon as the API runs on more than one instance (and run the `ratelimit.sweep` job, which `JOBS=1` includes). With one instance the default is correct.

Closed in the follow-up: ticket status links now expire (30 days after the ticket closes); the catering and public-lead
inquiry limiters use `lib/rate-limit.ts`; per-process counters are documented and have a shared option; unsubscribe GETs no longer act.
